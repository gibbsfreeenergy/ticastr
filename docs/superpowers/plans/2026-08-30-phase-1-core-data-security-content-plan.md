# Phase 1 Core Data, Content Storage, and Security Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Complete the first-priority correctness and security work for Ticastr: make MySQL the source of truth for article metadata and engagement, move article Markdown into versioned object assets, make storage-provider selection explicit and safe, and close the authentication, upload, browser-security, and abuse-control gaps.

**Architecture:** Keep one Spring Boot modular monolith. The `content`, `engagement`, `media`, `security`, and `administration` packages own use cases; MyBatis DAOs persist facts; `media` talks to a provider-neutral storage port; Redis is not required in this phase and the rate-limit port uses a bounded in-process implementation until Phase 2 supplies the Redis implementation.

**Tech Stack:** Java 21, Spring Boot 4.1, Spring Security, MyBatis/MyBatis-Plus, Flyway, MySQL 8, JUnit 5/Mockito/Testcontainers when Docker is available, Vue 3 Options API, Vite, Vitest.

**Spec:** [Ticastr single-instance architecture design](../specs/2026-08-30-ticastr-single-instance-design.md)

## Global Constraints

- Work only in the files named by the task or files required to keep that task compiling. The working tree already contains user-owned changes; do not reset, clean, or reformat unrelated files.
- Follow the repository's controller -> application/service -> DAO boundary. Persistence entities, request DTOs, and response VOs remain separate.
- Use `apply_patch` for source edits. Do not edit the tracked SQL dump or introduce a compatibility path for old article rows; the approved scope explicitly allows a clean data model without historical-data migration.
- Every behavior change follows RED -> GREEN -> REFACTOR. The RED step must run a focused test and record the expected failure before production code is added.
- Article Markdown is the canonical content. No new API, entity, mapper, DTO, search query, or cache may depend on `tb_article.article_content` after the cutover migration.
- Provider credentials are environment/deployment inputs only. Never add credential fields to a request DTO, response VO, database table, log statement, or frontend store.
- All object keys are generated by the backend from server-side IDs. A client-supplied path or original filename must never become an object key.
- Run `mvn -B -DskipTests=false test` and `mvn -B -DskipTests package` for the backend, plus the closest frontend checks, after the phase is complete. If Docker is unavailable, report the exact skipped integration tests instead of calling the phase fully green.

## Dependency Order

1. Establish contracts and focused tests so later changes cannot silently reintroduce article-body persistence or credential leakage.
2. Add the clean schema and persistence ports.
3. Implement provider adapters and the administrator-controlled active-provider registry.
4. Replace article-body persistence and reads with content assets.
5. Move engagement facts into MySQL and make Redis-independent behavior explicit.
6. Apply security and upload controls across all affected endpoints.
7. Update configuration, deployment contracts, API documentation, and phase-level verification.
